# Eduwit Spark: audit, 16 October 2026

Scope: the Spark app (`web`), its schema `b2c` on staging (`mplbspysxmtohnlwpbti`) and the staging deployment. The
production project was not touched. Findings outside Spark (Witty, the B2B CRM) are listed at the end for the record
and were **not** changed, as the limits require.

## Verdict

Spark is ready to go to production on the plan in `go-live-plan.md`. Nothing found in this pass blocks go-live; the
items fixed during the pass are in `b34`–`b36` and the app commits of 15–16 October. The b37 features (17 October) follow the same rules: every new function checks its caller, nothing new is executable by `anon`, the bulk send is capped at 50 and audited, and the health, audit and sign-in viewers are Admin-only (26 checks in `test_features`).

## Security

### Database (`b2c`)

| Check | Result |
| --- | --- |
| Row level security | On for all 102 tables. 71 policies, all `select` only; `authenticated` has no `insert`/`update`/`delete` on any table. 31 tables (queues, logs, codes, sessions, audit) have RLS on and **no** policy: nothing reads them directly, only functions. |
| Writes | Only through `SECURITY DEFINER` functions. Every one sets `search_path = ''`, resolves the caller with `b2c.uid()` and checks the role (`b2c.my_role()`, `b2c.require_role`). |
| `anon` | Can execute **0** functions in `b2c` (fingerprint column `anon_exec`). |
| Internal helpers | `setting`, `working_now`, `next_working_at`, `window_open`, `has_marketing_consent`, `period_conversion`, `email_allowance_left`, `call_suggestion`, `pending_set` are no longer executable by staff over the API (`b34`); checked by `test_walkthrough_fixes`. |
| Scoping | `followup_counts` was callable for any user id; now only for the caller unless Admin or sales head (`b34`). |
| Storage | No public buckets. Documents are read through signed URLs minted by the app after the role check. |
| Secrets in the database | API keys and signing secrets live in Vault (`vault.secrets`), never in `b2c.settings`; `app_deploy_set` writes the internal key there. |
| Lead data | `student_leads` is read through `b2c` views; Spark never writes to it. Phones are masked in lists (`maskPhone`) and shown in full only on the lead screen. |
| Fingerprint | Staging equals the local build from `b1`…`b38`: 392 functions, hash `395858d7…`, 103 tables, 72 policies, `anon_exec` 0 (after the System health fix of 15 Oct). |

Supabase advisors for `b2c`: no errors. The two warnings are by design and were reviewed function by function:
`rls_enabled_no_policy` on the 31 internal tables, and `authenticated_security_definer_function_executable` for the
186 API functions (each checks its caller). Performance advisors for `b2c`: no unindexed foreign keys (40 added in
`b34`), no `auth_rls_initplan`, no duplicate permissive policies; "unused index" is expected with no traffic yet.

### App (`web`)

| Check | Result |
| --- | --- |
| Dependencies | `npm audit`: 0 vulnerabilities. Next.js 16, React 19, `@supabase/ssr`. |
| Headers | HSTS (2 years, preload), `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (microphone, geolocation, payment, USB off; camera self only) in `next.config.ts`. |
| CSP | Per-request nonce in `proxy.ts`; `script-src 'self' 'nonce-…' 'strict-dynamic'`, `object-src 'none'`, `frame-ancestors 'none'`, `connect-src` limited to Supabase. |
| Sessions | Supabase cookies `httpOnly`, `secure`, `sameSite=lax`. New devices need the 6-digit email code; trusted devices are per user and revocable (Me → Devices). |
| Passwords | 12 to 128 characters (`lib/security.ts`); 5 failed passwords lock the account for 15 minutes; password links are signed with `LINK_SECRET`, work once, for one hour. |
| Server actions | Every action calls `assertUser` first and validates its input with zod before the RPC. |
| Routes | Internal routes (timers, jobs) require `x-internal-key`, compared in constant time (`lib/internal.ts`). Webhooks (WhatsApp, B2B) verify their HMAC signatures in constant time before anything is read (`lib/whatsapp.ts`, `lib/b2b-sign.ts`); Exotel does not sign its callbacks, so its URL carries a secret compared in constant time. |
| Open redirects | `safeNext` allows only same-site relative paths after sign-in. |
| Rate limits | Sign-in codes: 6 digits, 10 minutes, 5 attempts (`email_codes`); password links limited per address in `sign_in_log`; every attempt is logged with method and outcome. |
| Secrets | Read from the environment only; `assertStagingKey` refuses a production key in every test and script. Nothing is logged. |

### Deployment

- Vercel project `eduwit-b2c-crm` (team `eduwit`, Mumbai), variables set by `scripts/deploy-staging.mjs` from the
  environment; `LIVE_MODE` off; VAPID and `LINK_SECRET` generated once and kept.
- The database timers call the site with the internal key from Vault; every call returned 200 after the last deploy.
- Google sign-in uses a client restricted to the staging redirect; production needs its own (go-live step 3).

## Code

- TypeScript strict, `tsc --noEmit` clean; `next build` clean (no warnings).
- Duplicate helpers removed (`initials` now only in `lib/format`); sequential loads made parallel on Connectors, Me
  and the lead screen (`lead_detail` + `today` in one round trip); the sidebar's counts come from one `nav_counts`
  call per request instead of four.
- Jobs in the sync route stay sequential on purpose (they share the outbox).
- Tests: 96 unit tests (vitest), 346 SQL checks across seven suites, browser walkthrough of every screen per role and
  12 flows at laptop and phone size, all passing on the local build and against staging.

and predate Spark. Vikas may want them fixed by their own owners:

- 48 foreign keys without an index in `public` and `b2b`.

# Phase 1 and 2 (database layer) review

Second fresh, adversarial review of the Eduwit One database layer at HEAD `7c1b14f` on `claude/festive-babbage-7yhhx8`,
after the builder fixed B1 and M1 to M8 of `docs/reviews/phase-1.md`. The first review was not used as a guide; its
findings are referred to only where a fix is incomplete.

Scope: `supabase/migrations/*.sql` and every `.rollback.sql`, `supabase/checks/*.sql` (the sources of the generated
migration 0006), `supabase/tests/local/*.sql`, `supabase/tests/smoke.sql`, `scripts/db/*` and their tests,
`config/settings.json`, `config/defaults.json`. Rubric: spec §2, §5, §6, §7, §9, §13, §16, §17, D-001..D-046.

How it was checked, offline only: reading the code; `scripts/db/local-test.sh`, `npm test`, `npm run typecheck`,
`node scripts/db/guards.ts`, `node scripts/db/gen-checks.ts --check`; and probe scripts on throwaway local clusters
built the way `local-test.sh` builds its own (same stubs, same migrations, local PostgreSQL 16). The probes ran on an
export of commit `7c1b14f` (`git archive`), not on the working tree, which the builder changed while this review ran
(0002, 0003, 0007, the stubs and a new 0008 are out of scope). All line numbers are those of `7c1b14f`. App object
shapes were read from the migrations checked into `b2b-crm/`, `b2c-crm/` and `influencer-portal/`; the website
branch's production snapshot was not read, so Witty's own payload shapes are unverified. No remote database,
connector or network tool was used. A finding marked "verified" was reproduced on a local cluster or traced through the
code path end to end; anything else says "unverified" and why.

Severity: blocker = must be fixed before the production apply; major = a real failure on production that the phase
criteria would not catch; minor = a defect with limited reach or an unlikely trigger.

| B1 | blocker | supabase/migrations/0005_cron.sql:22-40; 0003_functions_runner.sql:100-108, :117-123; 0003_functions_runner.sql:80 (run_check's `when others`); D-044 | The committing procedure goes blind, silently, behind a fresh heartbeat, as soon as one step outlives `transaction_timeout` (30 s on PG 17). D-044 says a killed check "moves to the back" because checks run least-recently-started first. But `run_check_safe()` writes the start mark in the same transaction as the check, so the kill rolls the mark back: the slow check keeps the oldest mark, runs first again on the next minute, and is killed again. PG 17's `transaction_timeout` ends the whole session (FATAL), and a `statement_timeout` or cancel is `query_canceled`, which `when others` does not catch; either way every later check, every event source and the app call (the alert sender) are skipped on every tick. The heartbeat and the `one.runs` row are committed first, so `one:tick` stays fresh and the D-018 watchdog, which reads only that age, stays green. D-044's second safeguard, "a killed run fails visibly in cron.job_run_details (PLAT-01)", cannot work either: PLAT-01 never runs, and when it does it sees the current one-tick run as the latest run (M3). The local test (`10_core.sql` §10, "each check records its start before it runs") passes only because every check finished. Fix: commit the start mark in its own transaction before running the check (and the same per event source); make the watchdog's endpoint read the last finished tick (`one.runs.finished_at`), not only the heartbeat written at its start (ONE-01 runs inside the tick, so it cannot report this); test a check that is killed. | Supabase's IO budget runs out, or an app's health RPC or a query plan degrades, and one check takes over 30 s. On production the same happens at 30 s, every minute while the condition lasts: no check runs, no event is copied, no alert is sent, and nothing reports it. Unverified (no PG 17 locally): whether PG 17 restarts the timer at each `COMMIT` inside the procedure, as D-044 assumes; if it does not, the 30 s bound applies to the whole tick and is reached sooner (M7, M9). |

## Checked and found sound

Each item below was read in full; those marked (local) were also exercised on a local cluster.

- **Shared objects.** The migrations create only schema `one`, its two NOLOGIN roles, read grants with default
  privileges for the reader, EXECUTE on four health RPCs, and the two `one-*` cron jobs. They write nothing in any app
  schema and alter no app object. `lead_intake()`, `w2_*` and `catalog_*` are only read. The rollbacks touch only
  schema `one`, the two roles and the two jobs, and `leftovers.sql` proves nothing is left (local, `local-test.sh`).
  Every app call a check makes was checked for side effects: `b2b.health_check()`, `public.w2_health_alerts()`,
  `public.web_health()` and `inf.health()` are read-only, and `b2c.job_calls` is a single row of the last 600 ids.
- **Privileges.** Nothing in schema `one` is reachable by anon or authenticated: there is no USAGE on the schema, and
  EXECUTE is revoked from PUBLIC on every function and procedure. RLS is on for every table. Every function except
  `one.tick_job()` pins `search_path = ''` (smoke test). The service role cannot insert or delete a check or change
  its `sql`, `kind` or `search_path` (local, `20_events_secrets_privileges.sql` §5). `one.secret()` is executable by
  the owner only and refuses names outside `one_*` and the two app keys (local). `one.vault_names()` returns names
  only. The fixer holds nothing. Neither role has BYPASSRLS, CREATEROLE or SUPERUSER (smoke).
- **Dynamic SQL.** `run_check()` formats in check SQL that only migrations can write (column grants, plus the
  generator's and the table's keyword rules); `events_copy()` formats in constant source SQL from `events_sources()`,
  with `%L` for literals and `USING` for values; neither is executable by an API or app role. The per-check
  `search_path` takes only two values, and `public, pg_temp` keeps `pg_temp` last; it is safe only while no API role
  can create in `public`, which PLAT-06 and the smoke test watch through `one.public_schema_writers()`.
- **Event copy.** Nested PII keys are removed at any depth, through objects and arrays, and emails anywhere in a
  string and Indian-mobile numbers are masked (local; gaps in M5). `w2_messages` and the advisor, web-audit, partner
  and one-* sources build their payloads from explicit column lists. Lead ids are resolved through `crm_norm_phone`
  against an indexed `student_leads.whatsapp_number`, and the phone is never stored. The id overlap picks up late
  commits and the state sources record each status once (local, §1c, §1d).
- **AI inputs and alert evidence.** The triage task carries the incident id, the check id and the subjects (job
  names, partner slugs, Witty alert kinds), and the brief task carries a date. Check values carry counts, row ids,
  codes and timestamps. The error texts they carry verbatim (`return_message`, `webhook_endpoints.last_error`,
  `partner_programme_sources.last_error`) come from job errors and from Spark's handoff route, whose replies never echo
  request data (b2c-crm `web/app/v1/handoffs/route.ts`). Unverified: the texts of partner programme feeds.
- **Incident lifecycle.** Open, touch, recovery after `resolve_after` ok runs, and reopen within 24 h all behave as
  specified. A reopen, a P2-to-P1 escalation and a new subject each bump `alert_seq`, re-alert with a fresh delivery
  key, and clear the acknowledgement (local, `10_core.sql` §5 to §7, and own probes). `error` and `source_missing` now
  count as failures (M2 of the first review), staging opts out by setting, and `<ID>_error` reaches the report.
  `enqueue_alert()` returns the rows actually inserted.
- **Idempotency.** `one.tick()` and `tick_job()` take a unique minute bucket and `nightly()` an IST-day bucket, so a
  second call does nothing (local). Deliveries, triage and brief tasks, and actions are keyed. `settings_put()` skips
  equal values and never overwrites a person's edit. `seed_check()` upserts the rule and keeps a person's operational
  edits.
- **Check SQL against spec §6.** Every SQL check was read against its rule. Apart from the findings above, the
  following match their rule or a recorded decision (D-007, D-008, D-019, D-033 to D-040), and each excludes test rows
  where its table has the flag: PLAT-01B, PLAT-05, PLAT-07, PLAT-08, PLAT-09, B2B-01, B2B-03 to B2B-05, B2B-07 to
  B2B-14, B2C-02 to B2C-10, WEB-01, WEB-03 to WEB-06, INF-01 to INF-03, INF-05, INF-06, CAT-01 to CAT-04, INT-01 to
  INT-05 and INT-07. B2C-04 reads Spark's `working_defaults` in the shape Spark writes (b2c-crm `b1_access.sql:294`).
- **Generators and tests of the generators.** `gen-checks.ts` enforces the same rules as the `one.checks.sql`
  constraint, forbids comments and the `$sql$` tag inside check SQL, and requires every threshold key to exist in
  `config/settings.json`. `gen-seed.ts` refuses the `$seed$` tag. `--check` fails on drift, and `npm test` (11
  tests), `npm run typecheck`, `guards.ts` and both `--check` modes pass at `7c1b14f`.
- **Scripts.** Passwords travel only in `PGPASSWORD`, never in argv or output. `dump.sh` refuses a dump directory
  inside the repository, sends pg_dump's messages to a file, checks the client's major version, and writes a sha256
  that `apply.sh` verifies, together with a dump from the last 24 h. `with-db.ts` refuses a staging variable that
  reaches production and the reverse (unit test; the gap is m2). `apply.sh` refuses rollbacks and applies each file in
  its own transaction with `lock_timeout` and `statement_timeout`. The local tests refuse to run on any database but
  the throwaway cluster.

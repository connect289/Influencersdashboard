# Phase 1 and 2 (database layer) review

Second fresh, adversarial review of the Eduwit One database layer at HEAD `7c1b14f` on `claude/festive-babbage-7yhhx8`,
after the builder fixed B1 and M1 to M8 of `docs/reviews/phase-1.md`. The first review was not used as a guide; its
findings are referred to only where a fix is incomplete.

Scope: `supabase/migrations/*.sql` and every `.rollback.sql`, `supabase/checks/*.sql` (the sources of the generated
migration 0006), `supabase/tests/local/*.sql`, `supabase/tests/smoke.sql`, `scripts/db/*` and their tests,
`config/settings.json`, `config/defaults.json`. Rubric: spec §2, §5, §6, §7, §9, §13, §16, §17, D-001..D-046.

How it was checked, offline only: reading the code; `scripts/db/local-test.sh`, `npm test`, `npm run typecheck`,
`node scripts/db/guards.ts`, `node scripts/db/gen-checks.ts --check`; and probe scripts on throwaway local clusters
built the way `local-test.sh` builds its own (same stubs, same migrations, local PostgreSQL 16). App object shapes were
read from `b2b-crm/`, `b2c-crm/`, `influencer-portal/` and the website branch's production snapshot where needed. No
remote database, connector or network tool was used. A finding marked "verified" was reproduced on a local cluster or
traced through the code path end to end; anything else says "unverified" and why.

Severity: blocker = must be fixed before the production apply; major = a real failure on production that the phase
criteria would not catch; minor = a defect with limited reach or an unlikely trigger.

| M1 | major | supabase/checks/heartbeats.sql:14, :26, :37, :48, :59, :70, :81, :92, :103, :115, :127, :139, :151, :162, :173 (0006_seed_checks.sql, every HB-* block) | Every heartbeat check computes `ok` as `coalesce(h.last_ok_at > now() - …, true)`. The `coalesce(…, true)` was meant for "no row yet" (never_seen), but it also turns a row whose `last_ok_at` is null into ok. `one.heartbeat(c, false, …)` creates exactly that row: a component whose every probe has failed since the first one has `last_ok_at` null, `last_error_at` set, and is reported ok, with `never_seen: false` in the value, forever. Spec §2: "missing heartbeats are incidents"; §14 phase 2: "a deliberately broken staging probe produces an HB incident within 3 minutes" passes only for a probe that once worked. Fix: `ok = h.component is null or coalesce(h.last_ok_at > …, false)`, and test a row with only errors. | The website is down, or the probe's URL or token is wrong, from the day the prober is deployed. `one.heartbeat('website', false, '{}', 'HTTP 503', 60)` writes the row; `HB-website` (P1) returns `ok` on every run with value `{"last_ok_at": null, "last_error": "HTTP 503", "never_seen": false}` and opens no incident (verified on a local cluster). The same holds for `spark`, `vercel:one` and every other component. |
| M2 | major | supabase/checks/platform.sql:85; supabase/checks/heartbeats.sql:166-175; supabase/checks/one.sql:185-194; D-035, D-018 | When the database cannot reach the app, nothing fires, so no alert is ever delivered. The app is the alert sender (spec §3), reached only through `one.job_call('/api/internal/tick')`. (a) PLAT-04 counts only responses with status 401, 403 or 500 and up; pg_net records a timeout, a DNS or TLS failure or a refused connection with `status_code` null, which PLAT-04 skips (B2C-01's own call check does count null). (b) `HB-one:app` is ok while `never_seen`, with no end to that grace, even after `app.base_url` is set and calls are going out. (c) No check looks at the age of pending deliveries: ONE-01 counts `failed` ones only, and only the app could mark them failed. (d) The external watchdog of D-018 reads the one-tick age only, which stays fresh. Fix: count null-status responses in PLAT-04; make `HB-one:app` (and every HB-*) fail when never seen after a grace that starts when the component is expected (for one:app, when `app.base_url` is set; for probers, when their setup item is validated); add a check that a P1 delivery is still pending after a few minutes. | `app.base_url` is saved with a typo, or the Vercel function times out. A real P1 (PLAT-05 on the stubs) opens and queues its email. Ten ticks later, `net._http_response` holds 10 rows with `status_code` null and `timed_out` true, the email has been pending for 60 min, and PLAT-04, `HB-one:app` (value `never_seen: true`) and ONE-01 all report ok: 0 incidents (verified on a local cluster). The owner is never paged for anything until someone opens the UI. |
| B1 | blocker | supabase/migrations/0005_cron.sql:22-40; 0003_functions_runner.sql:100-108, :117-123; 0003_functions_runner.sql:80 (run_check's `when others`); D-044 | The committing procedure goes blind, silently, behind a fresh heartbeat, as soon as one step outlives `transaction_timeout` (30 s on PG 17). D-044 says a killed check "moves to the back" because checks run least-recently-started first. But `run_check_safe()` writes the start mark in the same transaction as the check, so the kill rolls the mark back: the slow check keeps the oldest mark, runs first again on the next minute, and is killed again. PG 17's `transaction_timeout` ends the whole session (FATAL), and a `statement_timeout` or cancel is `query_canceled`, which `when others` does not catch; either way every later check, every event source and the app call (the alert sender) are skipped on every tick. The heartbeat and the `one.runs` row are committed first, so `one:tick` stays fresh and the D-018 watchdog, which reads only that age, stays green. D-044's second safeguard, "a killed run fails visibly in cron.job_run_details (PLAT-01)", cannot work either: PLAT-01 never runs, and when it does it sees the current one-tick run as the latest run (M3). The local test (`10_core.sql` §10, "each check records its start before it runs") passes only because every check finished. Fix: commit the start mark in its own transaction before running the check (and the same per event source); have the watchdog's endpoint and ONE-01 fail when the last finished tick (`one.runs.finished_at`) is old, not only when the heartbeat is; test a check that is killed. | Supabase's IO budget runs out, or an app's health RPC or a query plan degrades, and one check takes over 30 s. Reproduced on PG 16 with a 3 s check and a 2 s timeout on the CALL as the stand-in kill: on three consecutive minutes the `one:tick` heartbeat was 2 s old, the slow check's `last_started_at` was still null (rolled back), 0 other checks ran, the run's report stayed `{}` and was never finished (verified). On production the same happens at 30 s, every minute while the condition lasts: no check runs, no event is copied, no alert is sent, and nothing reports it. |
| M3 | major | supabase/checks/platform.sql:11-18; supabase/checks/b2c.sql:13-16 | PLAT-01 ("latest run failed") and B2C-01 take each job's latest run whatever its status, including `starting` and `running`. Most app jobs run every minute or every few seconds and start at the top of the minute, as `one-tick` does, so when these checks run a second or two later the latest run of any job that takes longer than that is still in progress, and its previous failure is hidden. For `one-tick` itself the latest run is always the current one, so a failing tick can never be seen. Depending on where PLAT-01 falls in the tick order (it changes every minute), a slow failing job also flaps between fail and ok, which reopens and re-pages the incident. Fix: take the latest finished run (`status in ('succeeded', 'failed')`), and exclude `one-tick` from PLAT-01 in favour of a check on `one.runs` (B1). | `b2c-minute` fails every minute after about 5 s, and so does `one-tick`. With five such failures in the history and a run of each started 1 s ago, PLAT-01 returns ok with `failed_jobs: []` and B2C-01 returns ok with `failed_jobs: []` (verified on a local cluster). |

Fix: schedule the jobs in the last migration (and unschedule first in the rollbacks); make `events_copy()` refuse to copy, or use a built-in minimum list, when the configured list is missing or empty. | Applied up to 0005 only, then `call one.tick_job()`: `one.events` holds `b2b.events` 1 with `payload.changes.name = {"from": "<student name>", "to": "<student name 2>"}` and `b2c.events` 1 with `payload.text = "<free text about the student>"` and `payload.student_name = "<student name>"`. After 0006 and 0007 are applied, `events_refresh()` copies 0 rows and both payloads are unchanged (verified on a local cluster). |
| M5 | major | supabase/migrations/0004_events_union.sql:24-27, :35-40, :109, :118, :145; config/settings.json:178-215; supabase/tests/local/20_events_secrets_privileges.sql:40-48 | `one.redact()` masks a phone only when the whole string is phone-shaped (`^\+?[0-9][0-9 ().-]{8,20}$`).

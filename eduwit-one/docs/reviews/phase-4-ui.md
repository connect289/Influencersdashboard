# Phase 4 (UI) review

A fresh, adversarial review of Eduwit One phase 4 at commit `568f5ae` on `claude/festive-babbage-7yhhx8`.

**Scope.** The review covered:

- migrations `0009_auth`, `0010_ui_read`, `0011_ui_write`, `0012_ui_apps` and `0013_seed_builder_proposals`, with their rollbacks;
- the tests `70_auth.sql`, `80_ui_api.sql`, `90_ui_apps.sql` and `smoke.sql`;
- the whole web app: `middleware.ts`, `app/**`, `components/**` and `lib/**`.

Migrations 0001–0008 were read as context only.

**Rubric.**

- Spec §12 (pages and behaviours) and §13 (security), from the scratchpad `SPEC.md`. That file holds only §9 onwards, so §2 and §3 were taken as D-062 restates them.
- The phase 4 row of the build phases.
- D-055 to D-063.

**Method.** Everything was checked offline: by reading the code, and with these runs.

- **Test suites.** `scripts/db/local-test.sh` printed LOCAL TEST PASSED. In `web/`, `npx tsc --noEmit` was clean, `npx vitest run` reported 32 passed and 3 skipped, and `npx next build` succeeded.
- **Probe cluster.** A persistent throwaway PostgreSQL 16 cluster was built the same way as `local-test.sh`: the same stubs, then 0001 to 0013 (`review4/up.sh`). Every probe below ran there.
- **Shape check of every page read.** Fixtures went into every table a page reads (`review4/seed.sql`). Every `one.ui_*` read was then called as a signed-in owner, with `request.jwt.claims` set the way PostgREST sets it (`review4/dump.sql`). Each answer was parsed with the exact zod schema its page uses, by importing `web/lib/ui/schemas.ts` (`review4/validate.ts`). This ran three times: before any writes, after every kind of write, and after the app tables were added.
- **App tables.** These tables were added with the columns from the apps' own migrations in `b2b-crm/`, `b2c-crm/` and `influencer-portal/` (`review4/app_tables.sql`), so that every panel's SQL was really planned and run.
- **Phone layout.** Static copies of the phone layout of the incident and proposal pages were rendered in headless Chromium at 390 px, using the CSS from `next build` (`review4/measure2.mjs`).

**Limits.** No remote database, connector or network tool was used. The website's own functions (`web_*`, `w2_health_*`) are not in this repository, so their answers are unverified. PostgREST itself could not be run.

**Working tree.** While this review ran, another session added `e2e/` (a click-through) and changed `package.json`, `package-lock.json` and `.gitignore` in the working tree. No in-scope file changed, so every line number below is that of `568f5ae`. The only thing this review wrote under `eduwit-one/` is `web/.next` (the allowed `next build`).

**Labels.** "Verified" means the finding was reproduced on the local cluster or in Chromium, or traced through the code end to end. "Unverified" says why.

**Severity.**

- **Blocker:** a phase 4 acceptance criterion fails.
- **Major:** a real failure on production that the phase criteria would not catch.
- **Minor:** limited reach or an unlikely trigger.

## Checked and found fine

- **Test suites.** `local-test.sh` passes, including the rollback of 0009–0013 and re-apply. `tsc`, `vitest` and `next build` are clean.
- **Shape match, all 27 reads.** On realistic fixtures (owner, before and after every write kind), every `one.ui_*` read answer parses with the page's zod schema. Nullables, numeric versus string types, timestamps and the null "not found" answers all match.
- **Shape match, all 33 panels.** Every `ui_embed` answer matches `embedSchema`.
- **RPC argument names.** Every RPC argument name in `lib/actions/*`, the pages, the exports and the service-role auth calls matches its SQL signature: 21 writes, 20 reads, `auth_issue_code` and `auth_record`. Partial argument sets rely on SQL defaults.
- **Keyset pagination.** `next_before` / `p_before` work correctly in incidents, actions, proposals, audit and AI calls, and the "Older" links keep the active filters.
- **Gates.** `one.ui_require` runs first in every function `authenticated` can execute (smoke test and test 80). Owner-only: users, secrets and baselines. The recipients comparison covers p1, second contact, developer and sender, as `settings_check` defines them.
- **Settings versioning.** `ui_settings_put` writes a version through `settings_put`, with actor and reason. A restore is saved as a new version.
- **Sign-in flow.** It is functionally sound. The code is bound to the session, 5 tries and 5 codes an hour; the trusted device is kept as a hash. The `/auth/google` form POST gets a 303, because Next treats a urlencoded POST as an action, so the OAuth redirect stays GET.
- **Middleware.** It lets only static assets and `/api/*` through without a session. The console pages and both CSV exports require a session and `assertUser`. The machine routes are reachable.
- **Server actions.** Every one revalidates the pages it changes, and every form's field names match its action's zod schema.
- **States.** Every console page has empty, loading (`loading.tsx`) and error (`PageError` or `error.tsx`) states.
- **Panel SQL.** With the apps' real columns, every panel except `witty.replies` (M1) plans and runs: `b2b.partners`, allocations, `lead_campaigns`, `ad_spend_daily`; `b2c.fact_leads`, users, queues, `ad_spend_daily`; `inf.creators` and `link_clicks`; `b2b_referral_outcomes`; `web_funnel_events`.
- **Deep links.** The targets exist: Spark `/w` and `/s`, and the portal's `/admin`.
- **0013.** It is idempotent by `source_key`. Its rollback keeps decided proposals.
